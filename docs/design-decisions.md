| D11 | 2026-10-22 | ThingsBoard memory | The separate-services TB instance (core 1 GB, rule engine 1 GB, transport 512 MB) runs at ~970 MB of 1 GB in tb-core when idle (OOM risk under load); N=4 does not fit 16 GB with 1.5 GB tb-core. Postponed by the user ("decide later"); pilot uses N=1. Exploratory check (2026-10-22): tb-core OOM-killed at 1 GB during provisioning of 1000 devices (EXPL-tb-k4); user decision: exploratory runs at N=1 use tb-core/rule-engine 1536m, transport 768m, heap unchanged. Still open for N=4. | open |

| D15 | 2026-10-22 | Executor (user decision) | `constant-arrival-rate`, `seq = offset + iterationInTest`, valid only at 0 dropped iterations. The "identify dropped slots" requirement is removed: runs with drops are INVALID. Replaces D2's slot-schedule recommendation. | done |
| D16 | 2026-10-22 | Time resolution (user decision) | Millisecond timestamps (`*_ms`). Latency is computed from the scheduled time derived from seq. JS send time only feeds send lag; k6 sample time is authoritative where full JSON output exists. Send-lag gate: p99 <= 10 ms (configurable). Early-send check: no send > 2 ms before its scheduled time. | done |
| D17 | 2026-10-22 | Randomness (user decision) | Per-message randomness = `hash(seed, seq)` (Go/JS bit-identical); under thinning, seq is the tick index and the sent set is reproducible offline. | done |
| D18 | 2026-10-22 | Outputs (user decision) | Per-message records only for non-success outcomes (and early sends); everything else in 0..N-1 is ack_success. Send lag and ack latency as per-step bucketed histograms (Counters, not Trends). Full JSON output only for calibration runs. | done |
| D19 | 2026-10-22 | Step boundary | k6 runs r·d−1, r·d or r·d+1 iterations per step. r·d+1 is suppressed; r·d−1 was a real loss of the last tick with no drop counted (1 in 10 steps). Fix: executor runs 1 s past each step, only i < r·d is sent. 0 losses over 60 boundaries since. | done |
| D20 | 2026-10-22 | EdgeX status codes | The user expected 207 for success and failure on EdgeX. Measured: device-rest's ingestion endpoint answers 200 / 404. 207 batch answers come from the provisioning APIs (parsed item by item). The send path still parses a 207 if one appears. | done |

| D25 | 2026-10-22 | Tuning policy (user decision; user's D14) | A platform gets only (a) tuning its own official documentation recommends, or (b) fixes for defects in our deployment. Category A: leaves ack point, durability, delivery guarantee and batching semantics unchanged. Category B: changes any of these; needs the user's approval. Timebox: one working day of tuning per platform. Every change records its official source (URL + section, or repo file + tag), reason and expected effect, and goes into the manifest `deviations` of every later run. Durability-weakening settings (e.g. `synchronous_commit=off`) only in `DIAG-*` runs, labelled, never in `compose.yaml` / `.env.example`. | done |
| D26 | 2026-10-22 | Definition of k (user decision; user's D15) | k = number of cores in the application cpuset pool. At k = 1 every platform runs 1 replica per tier. Refines D7. | done |
