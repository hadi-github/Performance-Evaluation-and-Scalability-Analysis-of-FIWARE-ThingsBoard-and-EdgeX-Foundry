# Design decision log

Append-only. Each entry: the decision or conflict, its source, its status, and what it changes. "Spec" = the
2026-10-22 *Agent implementation plan: IoT workload harness with Go and k6*. Pilot-only choices stay marked as such
until a qualification freezes them.

| # | Date | Topic | Decision / conflict | Status |
|---|---|---|---|---|
| D1 | 2026-10-22 | Prior notes | The spec refers to attached `decisions.md`, `rqs.md` v2 and a 30-day plan, and to `AGENTS.md`. None of these exist in the project or on the workstation. Conflicts with those notes are **not checked**. This log records the spec against the project as it stood at commit `f00fb8d`. | open: add the notes to `docs/notes/` to check them |
| D2 | 2026-10-22 | Arrival identity | Native `constant-arrival-rate` loses planned-arrival identity and some arrivals under generator delay (docs/k6-feasibility.md, A2). Recommended: a script-owned deterministic slot schedule (native k6, passes the acceptance test); fallback: an xk6 slot dispenser. This deviates from the spec's "use constant-arrival-rate". | **decision pending (user)** |
| D3 | 2026-10-22 | Repository | Project turned into a git repository (`main`), one commit per milestone, so artifacts can record SHA and dirty state. Baseline commit `f00fb8d`. | done |
| D4 | 2026-10-22 | Pilot host | M0–M2 run on the workstation against local fixtures. Load-machine (ramonavm1) qualification is M3. | done |
| D5 | 2026-10-22 | Layout | The spec suggests `cmd/{benchctl,reference,sink}`, `internal/...`, `workloads/k6`, `workloads/plans`, `schemas`, `docs`, `tests/integration`. Adopted inside the existing project: one Go module `iotbench` at the root, new k6 code under `workloads/k6/`. The first-generation workloads (`workloads/*.js`, `run.sh`) stay as non-confirmatory smoke tools. | done |
| D6 | 2026-10-22 | First-generation k6 workloads | They identify devices and count arrivals with `iterationInTest`, which is the started-iteration counter, and judge validity from k6 aggregates. Under the spec they are **smoke tools only**; their results are not confirmatory evidence. | done |
| D7 | 2026-10-22 | Resource budget vs topology | The spec keeps the application-core budget k ∈ {1,2,4} and the replica topology as separate fields. The current stacks tie them (N instances ⇒ pool of N cores, `scripts/resources.mk`). Plan schema (M1) will separate them; `resources.mk` becomes "pool = k cores" with replicas set independently. | open (M1) |
| D8 | 2026-10-22 | Core allocation on the SUT | Spec: 1 core OS/Docker/exporters, supporting tier 3 cores, application k cores. Current: core 0 OS + exporters, core 1 HAProxy, cores 2-3 infrastructure, cores 4.. pool. HAProxy + infrastructure = the 3-core supporting tier. Consistent; HAProxy's CPU is counted as platform cost (spec §2). | consistent |
| D9 | 2026-10-22 | History for FIWARE | The spec requires retained history on all platforms (and names QuantumLeap). The current FIWARE stack is Orion + IoT Agent + MongoDB, and **Orion keeps only the latest value: there is no history.** A history component (QuantumLeap + its store) must be added and counted in platform CPU. | open (M4) |
| D10 | 2026-10-22 | Message contract (EdgeX) | Spec: one request = one logical reading with three numeric fields plus identity. The current EdgeX workload sends one field per request (device-rest takes one resource per call). Options: an Object-valued resource carrying all fields + identity, or another ingestion path. Must preserve identity in core-data history. | open (M4) |
| D11 | 2026-10-22 | ThingsBoard memory | The separate-services TB instance (core 1 GB, rule engine 1 GB, transport 512 MB) runs at ~970 MB of 1 GB in tb-core when idle (OOM risk under load); N=4 does not fit 16 GB with 1.5 GB tb-core. Postponed by the user ("decide later"); pilot uses N=1. | open |
| D12 | 2026-10-22 | Clocks | ramonavm1 had no working NTP (Ubuntu servers unreachable from Iran) and was 21.5 min behind. It now uses `ir.pool.ntp.org`/`ntp.day.ir` (timesyncd drop-in). Cross-machine uncertainty must be logged during runs and qualified (M3); an offset log alone is insufficient (spec §6). | partly done |
| D13 | 2026-10-22 | Dispatch timestamp | The dispatch event is the start of sending, taken from k6's `http_req` sample (time − `http_req_duration`, ns). JS `Date.now()` before `http.post` is not used as dispatch time: it lagged real dispatch by up to 2.2 s under generator starvation. | proposed (with D2) |
| D14 | 2026-10-22 | Workstation → ramonavm1 | Direct SSH from the workstation to ramonavm1 timed out intermittently (2026-10-21); it is reachable via `ssh -J root@ramonavm2`. Not a harness decision; affects operations only. | noted |
