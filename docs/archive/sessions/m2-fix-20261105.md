## Finding and correction

### M2-R1 — HIGH — case-insensitive JSON aliases bypassed strict exact-key validation

`internal/deployment/schema.go` (`decodeStrict`) relied on
`encoding/json.Decoder.DisallowUnknownFields`, which accepts case-variant field names. The separate
duplicate-key pass compared exact strings only. Consequently `platform`/`PLATFORM`,
`service`/`SERVICE`, `project`/`PROJECT`, `state`/`STATE` and a conflicting
`platform:"thingsboard"` plus `PLATFORM:"fiware"` were accepted. The evidence-manifest decoder had
the same risk.

**Correction:**

- Added a package-local `jsonShape` tree describing the exact, case-sensitive key set for the
  descriptor, inventory and evidence manifest, including every nested object and every object inside
  an array. Each shape marks optional keys; every other key is required.
- Added the shared raw-validation path `validateRawDocument` used by `DecodeDescriptor`,
  `DecodeInventory` and `DecodeEvidenceManifest`. It performs, before typed decoding:
  1. the existing recursive exact duplicate-key rejection at every nesting level and array element;
  2. explicit-null rejection;
  3. `validateExactShape`, which walks the parsed document, rejects unknown or non-case-exact keys,
     rejects missing required keys and recursively handles nested objects and array elements.
- Error paths are deterministic and explicit (keys are sorted before reporting), for example:
  - `descriptor: $: unknown or non-case-exact key "PLATFORM"`
  - `inventory: $.services[0].containers[0]: unknown or non-case-exact key "STATE"`
  - `evidence manifest: $: unknown or non-case-exact key "DOCUMENTS"`
- `decodeStrict` retains `DisallowUnknownFields` as defense-in-depth, but it is no longer the only
  check. No protocol package semantics were imported or changed.
- This is a strictness-only change: no schema field, default, allowlist, canonicalization, hash,
  PASS/FAIL state or output format was altered. Omitted required keys (for example `replica`) are now
  rejected explicitly instead of silently decoding to a zero value.

- descriptor root `PLATFORM` replacing or conflicting with `platform`;
- descriptor allocation, protocol optional key, provenance document array and service array aliases;
- descriptor service `REPLICAS` alias conflicting with the exact key;
- descriptor `effective_configuration.SHA256` alias;
- inventory root `PROJECT` replacing or conflicting with `project`;
- inventory service array alias and container array `STATE`, `HEALTH`, `STATE_REASON` aliases;
- evidence manifest `DOCUMENTS`, replaced `SCHEMA_VERSION` and document-array `SHA256` aliases.

Every case must return an error containing `unknown or non-case-exact key`; none may return `PASS`.

`TestDecodeRejectsDuplicateKeysInNestedObjectsAndArrays` has 7 subtests covering exact duplicate
keys at the root, inside a nested service object, inside a provenance-document array element,
inside an inventory container array element, inside an inventory service array element, at the
manifest root and inside a manifest document array element. Each must return
`duplicate JSON object key`.

`TestDecodeExactKeysAndKeyOrderPermutation` verifies valid descriptors, inventories and manifests
with caller-supplied manifest timestamp are still accepted in ascending, descending and rotated
top-level key orders with identical canonical output, and that a descriptor with both `platform`
and conflicting `PLATFORM` is rejected in every key order.
