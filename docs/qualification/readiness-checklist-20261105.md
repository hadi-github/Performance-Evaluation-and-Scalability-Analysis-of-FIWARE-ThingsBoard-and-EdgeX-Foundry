## Diagnosis: N=2 generator gate

- Both attempts used k6 `1.8.1`, container cpuset `0-2` (three generator cores), remote-write/recording enabled; the second pinned the sink to load-host core 3. No container throttling counters or SUT CPU-boundary snapshots were retained for those runs.
- First attempt: actual peak 50 VUs, 200 max allocated, k6 memory peak 415,305,728 B; host per-core busy maxima 29–36%. Second attempt: actual peak 4 VUs, 200 max allocated, 382,894,080 B; maxima 38–49%. Both had zero dropped iterations; the measurement step send-lag p99 was 6 ms. These observations do not support CPU saturation or VU starvation as the demonstrated cause.
- First attempt’s UNKNOWN seqs 0–17 all timed out at 5,000 ms (`transport:1050`, HTTP status 0); all 18 identities subsequently reached the sink. Of 3,300 scheduled identities, 3,186 had a sink receipt by capture end; all 114 absent identities were in warm-up, while all 3,000 measurement identities reached sink. Since all 18 UNKNOWN identities are among the 3,186 receipts, the 114 absent warm-up identities are among aggregate ACK outcomes; the legacy ledger has no success-per-message rows to name them. No retry/relabeling was performed. This is eventual delivery for 18 UNKNOWNs plus 114 acknowledged warm-up identities not observed at sink by cutoff; the run remains INVALID and supports no platform verdict.
- Second attempt has no per-message ledger rows because every request succeeded; all 3,300 unique sink identities arrived. Warm-up p99 send lag nevertheless remained 13 ms (p50 3 ms, max 15 ms). Thus the specific limiting component for the residual 3 ms gate overrun is **not identified** by retained instrumentation. The exact blocker is lack of scheduler-level delay, per-container throttle, and phase-aligned SUT counter evidence; do not relax 10 ms or rerun identically.
