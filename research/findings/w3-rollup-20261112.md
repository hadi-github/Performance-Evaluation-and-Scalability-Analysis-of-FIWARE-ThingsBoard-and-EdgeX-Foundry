# W3 roll-up: the payload survived on two platforms and is unobservable on the third

**Date:** 2026-11-12
**Workload:** W3 — 1,000 devices, 25 msg/s, 300 s warm-up + 600 s measurement,
`logical-json-ascii-v1` with **`size_offset_bytes=1024`**, 5,000 ms timeout, 150-VU pool.
**Scope:** qualifications. **None counts toward the 60 proposed attempts.**
**Batch position:** W1 (50/s, 1,000 devices), W2 (25/s, 2,000 devices) and W3 (25/s, 1,000
devices, +1,024-byte payload) are now measured on all three platforms except EdgeX W3.

---

## 1. Where W3 stands

| Platform | Run ID | Delivery verdict | Payload gate | p99 (measurement) |
|---|---|---|---|---|
| ThingsBoard | `w3-qual-tb-20261110` | `INVALID_PLATFORM_FAILURE_OR_BACKLOG` | **PASS** | 257.7 ms |
| FIWARE | `w3-qual-fw-20261110` | **`VALID_PLATFORM_SUCCESS`** | **UNAVAILABLE** | 407.3 ms |
| EdgeX | `w3-qual-ex-20261110` | not yet run | not yet measured | – |

The two columns disagree in opposite directions, and that is the honest result rather than a
contradiction:

- **ThingsBoard** stored and preserved the payload perfectly, and failed the delivery verdict
  on a warm-up cold-start ramp (213 of 7,500 identities not arrived by the cutoff; all 7,500
  reached history; the 600 s measurement was clean).
- **FIWARE** delivered flawlessly — the only W cell in this batch with zero unknown, zero
  missing and zero failed in *both* phases — but its stored payload is not observable at all,
  because the frozen subscriptions never forward `padding`.

A single "W3 passed / failed" column would misrepresent both of these.

## 2. ThingsBoard: the payload is proven byte-for-byte

Full account in `w3-thingsboard-payload-preserved-20261112.md`. In brief:

- **22,500 / 22,500** stored rows exported from `ts_kv.str_v` and validated by an independent
  check that rebuilds each expected payload from the plan seed;
- **every** row's padding is exactly **1,024 lowercase hex characters** (`{1024: 22500}`);
- **0** failures, **0** rows missing from the ledger;
- `logical_bytes` 1,208 = baseline 184 + 1,024.

The baseline histogram `{1205:182, 1206:2676, 1207:9895, 1208:9377}` confirms the arithmetic
per message: each row's target is its *own* baseline plus 1,024, and the baseline varies only
with the digit width of the identity fields — not with a fixed grid. A store that had padded to
a constant width would fail this.

## 3. FIWARE: delivery is clean, payload is unobservable

### 3a. The delivery result is the cleanest in the batch

| Phase | Scheduled | Received by cutoff | Missing | Unknown | Failed | History |
|---|---:|---:|---:|---:|---:|---:|
| warm-up (300 s) | 7,500 | 7,500 | **0** | **0** | **0** | 7,500 |
| measurement (600 s) | 15,000 | 15,000 | **0** | **0** | **0** | 15,000 |

Sink: 22,500 rows, 22,500 unique identities, **0** malformed, **0** truncated, **0** oversized,
**0** duplicates, **0** late. That matters specifically for W3: a 1,024-byte attribute passed
through the UltraLight encoder on every one of 22,500 messages and the transport never clipped
or rejected one.

Notably, **FIWARE showed no cold-start ramp at all**, unlike both ThingsBoard W cells, even
though the 1,000 devices were created immediately before traffic.

### 3b. The payload gate is unavailable, and proven unavailable

This is not an assumption from reading Source. It was confirmed against the live deployed
QuantumLeap database after the run:

```
SELECT t."padding" FROM mtopeniot.etsensor t
  WHERE t."run_id" = 'w3-qual-fw-20261110'
-> ERROR:  column t.padding does not exist
```

The 22,500 identity rows **are** in that table (`seq`, `run_id`, `scheduled_send_ms` all
populated), so this is a **projection** limit, not a delivery loss. The column list shows
`etsensor` has `entity_id, entity_type, time_index, fiware_servicepath, __original_ngsi_entity__,
instanceid, seq, run_id, scheduled_send_ms, temperature` — and no `padding`, `humidity` or
`pressure`.

Root cause, confirmed live against Orion's own API rather than inferred:

```
bench QL          -> ['seq','run_id','scheduled_send_ms','temperature']  normalized  inactive
bench sink        -> ['seq','run_id','scheduled_send_ms']                keyValues   active
bench quantumleap -> ['seq','run_id','scheduled_send_ms']                normalized  active
```

Both **active** routes omit `padding`. QuantumLeap creates typed columns only for forwarded
attributes, so nothing ever asks it to store the payload. `scripts/history-payload.sh fiware`
therefore exits **1** with zero rows emitted — it fails closed rather than regenerating padding
from the seed, which is exactly the behaviour gate 1b requires of a fake pass.

`payload-gate-unavailable.json` records this with the row counts and the exact error.

### 3c. What FIWARE *can* show, labelled as weak

Orion latest-state for the same run:

- **1,000 / 1,000** entities carry a `padding` attribute;
- **every** value is exactly **1,024** lowercase hex characters.

This proves the platform **ingests and stores** the padded payload end to end — it does not
reject, truncate or mangle it. It **cannot** prove per-message preservation: latest-state keeps
only the last value per entity, so 22,500 messages collapse to 1,000 surviving values.

That is recorded as **weak evidence, explicitly not gate 1b**, in
`orion-latest-state.json`. It is the strongest FIWARE payload signal obtainable without a
configuration change, and it narrows the uncertainty materially: the blocker is provably the
subscription projection, not the platform's ability to hold the payload.

### 3d. Gate 4, resolved with real padding

FIWARE's native UltraLight body is **1,089** bytes against **1,208** logical. The 119-byte gap
is the UltraLight encoding of the same identity fields. The `|d|` padding segment itself is
exactly **1,024** characters.

Gate 4's "native delta 1,022 vs logical 1,024" is the **zero-padding edge case** — quoted-empty
text encoding. With real padding the native segment carries all 1,024 characters, because a long
value is a single quoted string with no added encoding. Recorded as PASS with that distinction
stated, rather than quoting 1,022 where it does not apply.

## 5. Two decisions this raises (owner's, not the harness's)

1. **Warm-up cold-start policy.** W3 ThingsBoard is now the *second* case (after W2 TB) where a
   cell with a clean 600 s measurement is reported `FAILURE_OR_BACKLOG` purely because a
   cold-start warm-up had identities in flight at the cutoff. Every one of those identities
   reached history. Whether that should fail the cell is a measurement-policy decision, not a
   measurement.
2. **FIWARE subscription change.** The fix is prepared but **not applied**:
   `fiware-w3-payload-evidence-proposal-20261112.md` (Option A — add `padding` to the
   QuantumLeap subscription's `attrs`). It is a common-batch change that alters B0-era
   reproducibility, so it needs an owner decision, a new receipt bound to the edited launcher,
   and a comparability note. It was deliberately left untouched for this run.

## 6. A validator bug this batch exposed, and fixed

The first `payload-validate` pass on ThingsBoard reported 370 rows "missing from ledger". The
cause was the checker, not the platform: it expected only `ack_success` rows, while TB had
**stored** 370 warm-up messages whose acknowledgement the client never saw.

Payload preservation and delivery are different questions. `loadLedger` now includes every
dispatched message regardless of outcome. After the fix the same stored export validates
22,500/22,500 — no evidence regenerated, no row discarded. This is why the TB cell can carry a
`FAILURE_OR_BACKLOG` delivery verdict and a `VALID` payload verdict at the same time.

The checker is also proven against real data from an earlier independent run: it reproduces
18,000/18,000 rows of the `live-protocol-tb-n1-20261105T1340Z` export and agrees with the
prior validator (`stored_field_rows_validated: 18000`, `padding_empty: true`).
