### M2B-R1 (HIGH) — state gates now model the unchanged stacks

The orchestration schema is versioned to `deployment-orchestration-plan-v2`. Each declared Compose
service now carries three explicit properties:

- `lifecycle`: `persistent` or `one_shot`;
- `activation`: `default_start` or `optional_profile`;
- `healthcheck`: `declared` or `none`.

`EvaluateServiceExpectation` is a pure, offline predicate. A `one_shot` service passes only on a
supplied successful exit code `0`; running/healthy state is not completion evidence and a missing
exit code is `UNAVAILABLE`. A persistent service must be running with the declared replica count. An
explicit `healthcheck: declared` reports `healthy`/`unhealthy`; `unhealthy` is `FAIL` and missing
health evidence is `UNAVAILABLE`. `healthcheck: none` is a property, not a failed check: it requires
running plus functional evidence, and missing functional evidence is `UNAVAILABLE`. An
`optional_profile` service that is not activated is `NOT_ASSESSED`, not `FAIL`.

The declaration now represents every current Compose service, including the previously omitted
FIWARE `mongo-init`:

- ThingsBoard: three persistent application tiers; persistent supporting `zookeeper`, `kafka`,
  `postgres`, `valkey`, `haproxy`; optional one-shot `tb-install` behind the `install` profile with
  `restart: "no"` (not default-start; `NOT_ASSESSED` unless activated).
- FIWARE: persistent `orion`, `iot-agent`, `mongo`, `haproxy`; default-start one-shot `mongo-init`
  (`restart: "no"`; `orion` depends on `service_completed_successfully`).
- EdgeX: persistent `core-data`, `device-rest`, `database`, `nats`, `core-keeper`, `core-metadata`,
  `haproxy`; default-start one-shot `core-common-config-bootstrapper` (`restart: "no"`, exit 0
  required); optional-profile persistent `app-http-export` and `ui` (declared but not activated).

Validation rejects unknown lifecycle/activation/healthcheck values, a `one_shot` service with more
than one replica, and omission of any default-start service from the current stacks. The strict
exact-case-key, duplicate-key, explicit-null, trailing-JSON and schema-version checks remain in
force; there is no case-alias bypass. A v1 plan is rejected rather than reinterpreted.

The blueprint document now names `health: none` separately from a failed health result, states what
`one_shot` success means for the actual current jobs, documents `tb-install` as optional and
non-default-start, and labels unknown semantics `NOT_ASSESSED`/`UNAVAILABLE`.

### M2B-R2 (MEDIUM) — empty run identifier suffix rejected

`ArtifactManifest.Validate` now requires a non-empty run identifier suffix after
`{tag}-{YYYYMMDD}-` and rejects a repeated date separator. `m2b-fix-20261105-` and
`m2b-fix-20261105--x` fail closed; `m2b-fix-20261105-x` remains valid. Tests cover the exact-prefix
rejection, the repeated separator and the valid suffix.

### M2B-R3 (MEDIUM) — prior-manifest verification narrowed and marked

The packaging document no longer says `ArtifactManifest.Verify` implements rules 5–7. It now states
that `Verify` implements only rule 5 for the paths declared in the **current** manifest and does not
read a prior run's manifest. Rule 7 (binding a `preserved_prior` artifact to its own prior manifest)
is marked not implemented. `internal/deployment/packaging.go` exposes
`PriorManifestVerificationNotImplemented = NOT_IMPLEMENTED`, and a test proves that `Verify` does not
consult a prior manifest. The gate bullet now requires recording prior-manifest verification as
`NOT_ASSESSED`/`UNAVAILABLE` until a future reviewed workflow implements it.
